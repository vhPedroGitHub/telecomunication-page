    Programación en C del 8051 con SDCC

    En la vida profesional los microcontroladores se programan en C, y en ensamblador solo las rutinas críticas en tiempo. Pero el dominio de los recursos del µC (memoria, SFR, interrupciones) sigue siendo imprescindible: el C del 8051 tiene extensiones que solo se entienden si se conoce el hardware, y a veces hay que leer el ensamblador que genera el compilador.

    Objetivos (C15, C16)
    • Conocer las tareas de un compilador de C y las diferencias entre programar en C para un PC y para un µC.
    • Conocer las precauciones al programar un µC en C y las características del compilador SDCC.
    • Dominar los tipos de datos, de memoria y de interrupción de SDCC.
    • Analizar la relación entre el código C y el ensamblador generado y el efecto de las directivas sobre el mapa de memoria.
    C básico: tipos, punteros y operadores de bits

    unsigned char (8 bits, 0–255), operadores & | ^ ~ << >> para máscaras, punteros (*p, &x), volatile, while(1). Referencia: Kernighan y Ritchie, El lenguaje de programación C (en la bibliografía) · mapa de memoria del 8051 (Tema 2).

    1. ¿Qué hace un compilador de C?

    1. Expandir ficheros (cabeceras .h).
    2. Chequear la sintaxis (parser).
    3. Generar un fichero ASM equivalente a partir de patrones (su calidad depende del compilador).
    4. Ensamblarlo y enlazarlo con las bibliotecas.
    5. Obtener el .hex.

    Ficheros de SDCC: .c → .asm (equivalente) → .rel (+ .lst, .sym) → enlazador → .hex/.ihx (+ .rst, .map, .mem, .cdb para el simulador).

    2. C para PC frente a C para µC

    • Recursos muy distintos (incluso dentro de la misma familia); RAM muy limitada en los de 8 bits: cuidado con los tipos de datos.
    • La E/S estándar suele ser una UART: printf/scanf generan mucho código.
    • Extensiones no ANSI: tipos de bit, clases de memoria, interrupciones.
    • Conviene un asistente de configuración que genere la inicialización de periféricos.
    Precauciones (C15)
    • Evitar tipos sobredimensionados (y algunos no están soportados: SDCC no tiene double ni long double).
    • Evitar printf/scanf.
    • Evitar el desbordamiento de la pila: poco anidamiento, cuidado con la recursividad (muchos compiladores no lo detectan).
    • No optimizar antes de depurar: el optimizador puede eliminar for (i=0; i<1000; i++); (una demora «que no hace nada»). Las variables que cambian en una ISR deben ser volatile.

    3. SDCC (Small Device C Compiler)

    Compilador de C libre y de código abierto, optimizado para procesadores de 8 bits (8051 de muchos fabricantes, HC08/S08, Z80, STM8, PIC en desarrollo). Soporta ANSI C89 a ISO C17 con algunas restricciones. En MCU 8051 IDE: el tipo char es unsigned por defecto y, según la configuración, puede no reconocer los comentarios //. Compilación típica:

    sdcc -mmcs51 --iram-size 128 --xram-size 0 --code-size 8192 programa.c

    4. Tipos de datos

    TipoTamañoComentario
    __bit1 bitEn la zona 20h–2Fh. Extensión.
    char / unsigned char8 bitsEl tipo natural del 8051: úsalo siempre que alcance.
    short, int16 bitsOperaciones mucho más lentas que con char.
    long32 bitsMuy costoso.
    float32 bitsPor software: evitar.
    puntero1–3 bytesSegún el espacio al que apunta (genérico = 3).

    5. Clases de almacenamiento (zonas de memoria)

    Hay que decir al compilador en qué memoria va cada variable:

    ClaseZonaAcceso
    __codeMemoria de programa (constantes, tablas)movc
    __data128 bytes bajos de la RAM internaDirecto (el más rápido)
    __idata256 bytes de RAM internaIndirecto (@R0, @R1)
    __xdataMemoria de datos externamovx
    __bitZona direccionable bit a bit (20h–2Fh)Instrucciones de bit
    __sfr / __sfr16 / __sbitRegistros de funciones especiales / pares de SFR / un bit de SFRDirecto · de bit

    Punteros: se especifica la clase de la variable puntero y la de la memoria a la que apunta: __xdata char * __data puntero; (puntero almacenado en __data que apunta a __xdata). Se implementan con R0, R1 o DPTR.

    5.1 Direccionamiento absoluto

    Con __at (dirección) se fija dónde va algo (el compilador no detecta solapamientos):

    __code __at (0x300) char Id[5] = "SDCC";
__code __at (0x100) char Tabla7Seg[] = {0x40, 0x79, 0x24, 0x30, 0x19, 0x12, 0x02, 0x78, 0x00, 0x18};
__bit  __at (0x02) Fin_Adq;
volatile __data __at (0x30) char ADC_Values[50];   // volatile: puede cambiarla una ISR o el HW
__sfr16 __at (0x8C8A) TMR0;                         // TH0 (8Ch) : TL0 (8Ah)

    Los SFR y sus bits ya están declarados en <8051.h> (equivalente al .inc del ensamblador): __sfr __at (0x80) P0;, __sbit __at (0xD7) CY;, máscaras como T0_M0 = 0x01, T1_M1 = 0x20 para formar TMOD con OR, y los números de vector IE0_VECTOR 0, TF0_VECTOR 1, IE1_VECTOR 2, TF1_VECTOR 3, SI0_VECTOR 4. Así CY = 0; P0 = 0x55; TMR0 = 0x3CB0; genera clr C, mov 80h,#55h, mov 8Ch,#3Ch, mov 8Ah,#0B0h.

    6. Bancos de registros y rutinas de interrupción

    SDCC usa el banco 0 para sus operaciones (punteros, temporales). Una función puede usar otro banco con __using (n). El enlazador coloca la pila después de la última variable y avisa si no hay memoria suficiente.

    void timer1_isr (void) __interrupt (3) __using (1);   // vector 3 = Timer 1, banco 1

    El número de __interrupt es el número de vector (0 = INT0 en 03h, 1 = Timer 0 en 0Bh, 2 = INT1, 3 = Timer 1, 4 = puerto serie). Con __using el compilador salva PSW (y A, B, DPTR si hace falta) y cambia de banco; sin él, salva todos los registros que use. Para insertar ensamblador: __asm … __endasm; o en línea __asm__ ("NOP");.

    7. El sistema de la C14 en C (C16)

    #include <8051.h>
#define TMOD_CONF 0b00100001       // T1 modo 2; T0 modo 1
#define TMR0_REC  0x3CB0           // 50 ms
#define TMR1_REC  230              // 1200 baudios
#define SCON_CONF 0b01010000       // modo 1, Rx habilitada
#define INIC_AD   P3_4
__sfr16 __at (0x8C8A) TMR0;

void intr_ADC  (void) __interrupt (0) __using (2);   // INT0
void intr_50ms (void) __interrupt (1) __using (2);   // Timer 0
void intr_UART (void) __interrupt (4) __using (2);   // UART

volatile __data unsigned char ADC_Values[50];
volatile __data unsigned char Cont_m, Cont_1s;
volatile __bit Fin_Tx;
__code const char Tabla7Seg[] = {0x40, 0x79, 0x24, 0x30, 0x19, 0x12, 2, 0x78, 0, 0x18};

void main (void) {
  TMR0 = TMR0_REC; TH1 = TMR1_REC; TL1 = TMR1_REC;
  TMOD = TMOD_CONF;
  IT0 = 1;                          // INT0 por flanco de caída
  while (1) {
    P1 = 0x40; P2 = 0x40;           // display en 00
    Cont_m = 0; Fin_Tx = 0; Cont_1s = 20;
    IE = 0b10000011;                // EX0 y ET0
    TR0 = 1;
    while (Cont_m < 50);            // esperar las 50 muestras
    TR0 = 0;
    SCON = SCON_CONF; TR1 = 1;
    IE = 0b10010000;                // ES
    while (!Fin_Tx);                // esperar el fin de las Tx
  }
}
void intr_ADC (void) __interrupt (0) __using (2) {
  ADC_Values[Cont_m] = P0;
  P1 = Tabla7Seg[++Cont_m / 10];    // decenas
  P2 = Tabla7Seg[Cont_m % 10];      // unidades
}
void intr_50ms (void) __interrupt (1) __using (2) {
  TMR0 = TMR0_REC;
  if (--Cont_1s == 0) { Cont_1s = 20; INIC_AD = 0; __asm__ ("NOP"); INIC_AD = 1; }
}
void intr_UART (void) __interrupt (4) __using (2) {
  if (RI) {                         // prioridad a la Rx
    RI = 0;
    if (SBUF == 0xAA) { Cont_m = 0; REN = 0; TI = 1; }
  } else {
    TI = 0;
    if (Cont_m == 50) Fin_Tx = 1;
    else SBUF = ADC_Values[Cont_m++];
  }
}

    En la diapositiva de la C16 la tabla aparece como {0x40, 0x79, 0x44, 0x60, 0x31, …}; aquí se usa la de la C14 (0x24, 0x30, 0x19), coherente con la conexión a → bit 0 (ver Tema 4).

    7.1 Lo que genera el compilador

    • En 0000h, ljmp __sdcc_gsinit_startup: código de inicialización de la biblioteca (limpia RAM, inicializa SP y variables) que aumenta tamaño y tiempo.
    • En los vectores no usados, reti; en los usados, ljmp _intr_….
    • intr_ADC empieza con push acc / push b / push dpl / push dph / push psw / mov psw,#0x10 (banco 2): en este caso solo hacía falta PSW, «pero el compilador no lo sabe».
    • ++Cont_m/10 y Cont_m%10 generan dos div ab y dos mov dptr,#_Tabla7Seg: redundancia que en ensamblador se evita (un solo div da cociente y resto).
    • En intr_50ms el optimizador elimina el cambio de banco y los push innecesarios (lo indica con comentarios ; eliminated unneeded…).

    8. Guía de la CP8

    Los ejercicios son los de la CP7 programados en C: 90 muestras cada 5 s, bocina a 4 kHz (Timer 1 no puede: está generando el BR → bocina con Timer 0 en modo 2 y la base de 5 s contando desbordamientos de 125 µs, o al revés), comandos 1–6 a 2400 baudios con paridad par (modo 3: TH1 = 256 − 12·10⁶/(384·2400) = 242,98 → 243; error 0,16 %). Paridad en C: ACC = dato; TB8 = P; (P del PSW). Declarar las ISR con __interrupt(n), las variables compartidas volatile, y decidir en qué clase de memoria va cada buffer (90 bytes no caben junto al resto en __data: usar __idata en un 8052).

    Autoevaluación

    1. ¿Qué número de __interrupt corresponde al Timer 0?

    Número de vector, no dirección: 0Bh es el vector 1.

    2. Una variable que modifica una ISR y lee el main debe ser…

    Para que el optimizador no la guarde en un registro y la lea siempre de memoria.

    3. Una tabla de constantes se declara…

    En memoria de programa, sin gastar RAM.

    Preguntas frecuentes

    ¿Por qué mi demora con for no tarda nada?

    El optimizador vio que el bucle no hace nada y lo eliminó. Usa una variable volatile, inserta __asm__("NOP") o, mejor, un timer.

    ¿Cuándo vale la pena el ensamblador?

    En rutinas críticas en tiempo (ISR muy frecuentes, protocolos por software) o cuando hay que ajustar ciclos exactos. Para el resto, C es más productivo y mantenible.

    ¿Por qué SDCC pone el stack «después de las variables»?

    Porque la pila del 8051 crece hacia arriba: lo más alto de la RAM libre queda para ella. El enlazador avisa si las variables más la pila no caben.
